계층형 아키텍처는 코드에 나쁜 습관이 스며들기 쉽다. 시간이 지날수록 소프트웨어를 점점 더 변경하기 어렵게 만든다.

# 계층형 아케틱처는 DB 주도 설계를 유도

계층형 아키텍처의 토대는 데이터베이스다. 웹 계층은 도메인 계층에 의존하고, 도메인 계층은 영속성 계층에 의존하고, 영속성 계층은 DB에 의존한다.

따라서 모든 영속성 계층이 DB에 의존적이다. 그래서 다양한 문제들이 발생할 수 있다.

우리는 상태가 아닌 행동을 중심으로 모델링을 한다. 왜냐하면 행동이 상태를 변경시키는 주체이기 때문이다. 즉, 행동이 비즈니스 로직을 이끌어간다.

전통적인 계층형 아키텍처의 경우, 도메인 로직을 먼저 작성하는 것이 아니라 영속성 계층을 먼저 구현했다. 즉, DB 구조를 설계하고 이를 기반으로 도메인 로직을 작성했을 것이다.

> 하지만 비즈니스 관점에서는 좋지 않은 방법이다. 결론적으로 도메인 로직을 먼저 만들어야 한다. 그래야만 우리가 로직을 제대로 이해했는지 확인할 수 있다. 도메인 로직이 맞다는 것을 확인한 후에 이를 기반으로 영속성 계층과 웹 계층을 만들어야 한다.

DB가 중심인 아키텍처가 만들어지는 이유는 ORM이 가장 크다. 하지만 ORM을 계층형 아키텍처와 결합하면, 비즈니스 규칙을 영속성 관점과 섞고 싶은 유혹을 쉽게 받는다.

일반저긍로 ORM에 의해 관리하는 엔티티의 경우 영속성 계층에 둔다. 그래야 도메인 계층에서 영속성 계층인 엔티티에 접근할 수 있기 때문이다.

> 하지만 이런 경우 영속성 계층과 도메인(서비스) 계층 사이에 강한 결합이 생긴다. 따라서 서비스는 영속성 모델을 비즈니스 모델처럼 사용하게 된다.

영속성 코드가 도메인 코드에 들어가면서 둘 중 하나만 바꾸는 것이 어려워지고, 유연하고 선택의 폭을 넓히는 계층형 아키텍처의 목표와는 다르게 흘러간다.

# 지름길 선택이 쉽다

만약 상위 계층에 접근하고 싶은 경우, 간단하게 컴포넌트를 계층아래로 내려버리면 된다. 그러면 접근도 깔끔하다.

하지만 시간이 지날수록 영속성 계층은 점차 비대해진다. 영속성 계층은 컴포넌트를 아래 계층으로 내릴수록 비대해진다. 어떤 계층에도 속하지 않은 것처럼 보이는 헬퍼 컴포넌트, 유틸리리 컴포넌트들이 이처럼 아래 계층으로 내릴 가능성이 큰 후보다.

> 적어도 추가적인 아키텍처 규칙을 강제로 하지 않는 한 계층은 최선의 선택이 아니다.

# 테스트하기 어렵다

엔티티의 필드를 단 하나만 조작하면 되는 경우에 웹 계층에서 바로 영속성 계층에 접근하면 도메인 계층을 건드릴 필요가 없지 않을까?

2가지의 문제점이 생긴다.

> 1. 단 하나의 필드를 조작하는 것이여도 도메인 로직을 웹 계층에 구현하게 된다는 것이다. 만약 유스케이스가 확장된다면 어떻게 될까? 이런 경우, 더 많은 도메인 로직을 웹 계층에 추가해서 APP 전반에 걸쳐 책임이 섞이고 핵심 도메인 로직들이 퍼져나갈 확률이 높다.

> 2. 웹 계층 테스트에서 도메인 계층뿐만 아니라 영속성 계층도 모킹해야 한다. 단위 테스트의 복잡도가 올라간다. 그리고 테스트 설정이 복잡해지는 것은 테스트를 전혀 작성하지 않는 방향으로 가는 첫걸음이다.

시간이 흘러 웹 컴포넌트의 규모가 커지면 다양한 영속성 컴포넌트에 의존성이 많이 쌓이면서 테스트의 복잡도를 높인다. 어느 순간에는 실제로 테스트 코드를 작성하는 것보다 종속성을 이해하고 목을 만드는 데 더 많은 시간이 걸리게 된다.

# 유스케이스를 숨긴다

새로운 유스케이스가 추가되는 경우, 점차 도메인(서비스) 계층은 두꺼워지고 영속성 계층에게 많은 의존을 하게 된다. 따라서 서비스를 테스트하기도 어렵고, 작업해야 할 유스케이스를 책임지는 서비스를 찾기도 어렵다.

# 동시 작업이 어렵다

경영진은 소프트웨어가 특정 날짜에 완성되기를 바란다. 하지만 계층형 아키텍처를 하면 점차 복잡도가 올라가 동시작업과 시간이 늘어난다.
